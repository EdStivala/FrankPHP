Every FrankPHP project has two files that, together, tell an AI assistant — or a new developer — everything they need to know:

| File | Describes | Who keeps it up to date |
|---|---|---|
| `framework/codebase.md` | FrankPHP itself | FrankPHP. It's replaced on every update, so don't edit it. |
| `app/MYAPP.md` | Your app | You |

This page covers what goes in MYAPP.md, and how to keep it accurate.

---

## What goes in it

MYAPP.md records everything your app adds on top of FrankPHP:

- every table your app creates
- every route your app registers
- every controller, model and service you add
- the business rules that aren't obvious from the code
- anything your app does differently from FrankPHP on purpose

It leaves out anything `codebase.md` already covers: the `tenants`, `users`, `login_codes` and `invites` tables, the sign-in and settings routes, the middleware, and FrankPHP's own email flows. Mention them by name where your app uses them — "linked to `users.id`" — but don't describe them again.

<Note>
Think of MYAPP.md as the one document a new developer, or a new AI session, would need to understand your app without reading every file.
</Note>

---

## Why it must stay accurate

An AI assistant working from an out-of-date MYAPP.md fills the gaps with guesses — guesses that sound right and are wrong in ways that are hard to spot. The more accurate the file, the better the code you get first time.

---

## Keeping it up to date

How it's updated depends on how you're working:

<Tabs>
  <Tab title="With an AI agent">
    An agent that can edit your files — such as Claude Code — updates MYAPP.md **as part of the same task** as the code. It should:

    1. write the code
    2. update the right sections of MYAPP.md
    3. tell you which sections it changed

    If it writes code without updating MYAPP.md, ask it to finish the job before you move on.
  </Tab>
  <Tab title="With a chat assistant">
    At the start of each session, paste in both `framework/codebase.md` and `app/MYAPP.md`.

    After it writes code, the assistant gives you a labelled **MYAPP.md PATCH**: the exact lines to add, change or remove, and where. Apply it before your next session.
  </Tab>
  <Tab title="By yourself">
    If you add a route, model or service by hand, update MYAPP.md yourself before your next AI session. Each section explains what belongs in it.
  </Tab>
</Tabs>

Whoever makes the change, the section to update is the same:

| What you built | Section to update |
|---|---|
| A new table | Data Model |
| A new route, controller or controller method | Route Inventory |
| A new model with methods of its own | Models |
| A new service, or a new container recipe | Services — say whether it's a `singleton` or a `bind` |
| A new business rule | Business Rules |
| Something done differently from FrankPHP on purpose | Known Deviations |
| A new CSS file or reusable class | CSS Conventions |

<Tip>
Changed how FrankPHP behaves — for example, [sending new people somewhere else](/cookbooks/send-new-people-elsewhere), or turning terms off? Record it under **Known Deviations**, so nobody "fixes" it back.
</Tip>

## The sections worth extra care

### Current Development Focus

This section says what you're working on now. It sits near the end of the file, but it's the first thing an AI agent should read. Update it whenever you start a significant piece of work:

```markdown
## Current Development Focus

- **Current feature:** Building the invoice flow
- **Working files:** InvoiceController.php, InvoiceService.php, Views/invoices/
- **Patterns to follow:** Follow CustomerController@save
- **Known issues / tech debt:** InvoiceService is getting large
- **Do not touch:** PaymentService is stable — don't refactor it
```

### Roles

Say what `owner` and `user` can do in **your** app. FrankPHP supplies the roles; what they mean is your decision.

### Business Rules

Write out any rule that isn't obvious from the code — for example, "a session can't start if the person already has one unfinished". These are exactly the rules an AI assistant is most likely to break.

### Glossary

Define words that mean something particular in your app: "a Tenant is a gym", "a Session is a workout, not a web session". Obvious to you, ambiguous to an AI reading the code cold.
