# Getting Email Up and Running

By the end of this guide, you will have configured transactional email services for FrankPHP. You'll ensure that system-level triggers (like platform alerts and user signups) work out of the box, and you'll understand how to dispatch emails down to your individual tenant users.

FrankPHP relies on a robust, zero-dependency SMTP configuration mapped through standard PHP environment variables. Like the database setup, it requires no external package builders.

---

## Step 1: Understand the Email Architecture

Before writing config values, it's essential to understand how FrankPHP routes communication. The framework differentiates between two distinct directions of flow:

* **Platform-to-Owner (Upward/System Alerts):** Automated operational triggers sent from FrankPHP directly to you (the `MAIL_SITE_ADMIN`), or automated alerts sent to a Tenant Owner when significant structural events happen.
* **Owner-to-User (Downward/Transactional):** Functional, programmatic transactional emails driven by application events—such as password resets, verification codes, or a Tenant Owner pushing invitations down to new individual users.

<Warning>
**Transactional Only:** FrankPHP’s email architecture is designed strictly for **transactional emails** (system notifications, invites, resets). It is not built or intended for marketing newsletters, sequence blasts, or bulk promotional tracking.
</Warning>

---

## Step 2: Configure Your Environment Credentials

Open your `app/.env` file (which you created during the initial server installation). You will find the SMTP configuration block waiting for your credentials:

```php
# ---------------------------------------------------------------
# EMAIL (SMTP via PHPMailer)
# ---------------------------------------------------------------
MAIL_HOST=smtp.yourmailprovider.com
MAIL_PORT=587
MAIL_USERNAME=your_smtp_username
MAIL_PASSWORD=your_smtp_password
MAIL_FROM_ADDRESS=you@yourdomain.com
MAIL_FROM_NAME="Your App Name"
MAIL_REPLY_TO=you@yourdomain.com

# ---------------------------------------------------------------
# EMAIL (Recipient of Platform Level Alert Messages)
# ---------------------------------------------------------------
MAIL_SITE_ADMIN=admin@yourdomain.com
```

### Configuration Checklist

* **`MAIL_HOST` & `MAIL_PORT`:** Provided by your SMTP provider (Mailgun, Postmark, SendGrid, Amazon SES, or your shared hosting mail server).
* **`MAIL_FROM_ADDRESS`:** The address your users see. Ensure this matches your domain SPF/DKIM records to guarantee high deliverability.
* **`MAIL_SITE_ADMIN`:** The absolute root address where you want to receive framework-level alerts (e.g., system exceptions, security flags, or platform notification updates).

## Step 4: Customising Email Templates

FrankPHP avoids complex, bloated templating engines. Following the framework philosophy of *"explicit over magic,"* email layouts are constructed dynamically using standard PHP objects.

`EmailService` triggers three framework-owned flows directly — signup verification, password reset, and the platform-owner signup alert — each rendered by a default template class shipped inside `framework/Services/Email/Templates/`.

<Warning>
**Never edit those template files directly.** They live inside `framework/`, so any change you make there is silently lost the next time you update the framework. Override the template *class* instead — via config.
</Warning>

Add an entry to `mail.templates` in `app/Config/config.php`, mapping the flow you want to change to your own replacement class:

```php
// app/Config/config.php
'mail' => [
    // ...existing keys...
    'templates' => [
        // 'signup_verification'         => \App\Email\Templates\MySignupVerificationTemplate::class,
        'password_reset'                 => \App\Email\Templates\MyPasswordResetTemplate::class,
        // 'platform_owner_signup_alert'  => \App\Email\Templates\MyPlatformOwnerAlertTemplate::class,
    ],
],
```

Your override class must implement the same static methods, with the same arguments, as the framework default it replaces:

| Flow key | Required static signature |
|---|---|
| `signup_verification` | `buildHtml(string $email, string $code, int $expiry): string` and `buildText(string $email, string $code, int $expiry): string` |
| `password_reset` | `buildHtml(string $name, string $resetUrl): string` and `buildText(string $name, string $resetUrl): string` |
| `platform_owner_signup_alert` | `buildHtml(string $email, string $event): string` and `buildText(string $email, string $event): string` |

For example, a password reset override:

```php
// app/Email/Templates/MyPasswordResetTemplate.php
namespace App\Email\Templates;

class MyPasswordResetTemplate
{
    public static function buildHtml(string $name, string $resetUrl): string
    {
        return "
            <div style='font-family: sans-serif; padding: 20px; color: #1f2937;'>
                <h2>Hello, " . htmlspecialchars($name) . "</h2>
                <p>We received a request to reset your password for your account.</p>
                <p><a href='" . htmlspecialchars($resetUrl) . "' style='background: #6366f1; color: white; padding: 10px 20px; text-decoration: none; border-radius: 6px; display: inline-block;'>Reset Password</a></p>
                <p>If you did not make this request, you can safely ignore this email.</p>
            </div>
        ";
    }

    public static function buildText(string $name, string $resetUrl): string
    {
        return "Hello {$name},\n\nReset your password: {$resetUrl}\n\nIf you did not request this, ignore this email.";
    }
}
```

The override class can live anywhere under `App\` — it doesn't need to sit in any particular folder.

<Note>
A fresh install's `templates` map is empty, so this is entirely opt-in. Nothing needs configuring for a new project to send correct, framework-default email — you only add an entry here once you want your own wording or branding on one of the three framework flows.
</Note>

## Step 5: How to Trigger an Owner-to-User Notification

When building new features, you will often need to let a Tenant Owner push communications downward to their users. `EmailService` only ships the three framework-owned flows above — for a new email type, the pattern is an **application-owned service** that builds its own message and calls `EmailService::send()` directly. Following the *"delegate, don't decide"* pattern, your controllers should never handle email construction themselves.

Here's the full pattern for a custom "invite a team member" notification.

**`app/Services/NotificationService.php`**

```php
<?php

namespace App\Services;

use Frank\Services\Email\EmailService;
use Frank\Services\Email\EmailMessage;
use Frank\Services\Email\EmailResult;

class NotificationService
{
    public function __construct(
        private EmailService $emailService,
        private string $mailUsername,
        private string $mailPassword,
        private string $fromEmail,
        private string $fromName
    ) {}

    public function sendUserInvite(string $email, string $name, string $inviteUrl): EmailResult
    {
        $htmlBody = "
            <div style='font-family: sans-serif; padding: 20px; color: #1f2937;'>
                <h2>You're invited</h2>
                <p>" . htmlspecialchars($name) . " has invited you to join their team on the app.</p>
                <p><a href='" . htmlspecialchars($inviteUrl) . "'>Accept invitation</a></p>
            </div>
        ";

        return $this->emailService->send(new EmailMessage(
            credentialsUserName:   $this->mailUsername,
            credentialsUserSecret: $this->mailPassword,
            to:       $email,
            toName:   $name,
            subject:  "You're invited to join the team",
            htmlBody: $htmlBody,
            from:     $this->fromEmail,
            fromName: $this->fromName,
        ));
    }
}
```

**In `app/bootstrap.php`:**

```php
$container->singleton(\App\Services\NotificationService::class, function ($c) use ($config) {
    return new \App\Services\NotificationService(
        $c->make(\Frank\Services\Email\EmailService::class),
        $config['mail']['username'],
        $config['mail']['password'],
        $config['mail']['from_address'],
        $config['mail']['from_name'],
    );
});

$container->bind(\App\Controllers\TeamInvitationController::class, function ($c) {
    return new \App\Controllers\TeamInvitationController(
        $c->make(\App\Services\NotificationService::class)
    );
});
```

**`app/Controllers/TeamInvitationController.php`**

```php
<?php

namespace App\Controllers;

use Frank\Core\BaseController;
use Frank\Core\Request;
use Frank\Core\Response;
use App\Services\NotificationService;

class TeamInvitationController extends BaseController
{
    public function __construct(
        private NotificationService $notificationService
    ) {}

    public function sendInvite(Request $request, array $params): mixed
    {
        // 1. Fetch targeted recipient details from form input
        $targetEmail = $request->input('email');
        $targetName  = $request->input('name');
        $inviteUrl   = "https://app.yoursite.com/signup?invite=token123";

        // 2. Instruct your own notification service to build and dispatch the email
        $result = $this->notificationService->sendUserInvite($targetEmail, $targetName, $inviteUrl);

        if ($result->success) {
            return Response::redirect("/tenant/{$request->tenant['id']}/team?success=invited");
        }

        // 3. Gracefully return execution errors to the view layer
        return $this->view('team/invite', [
            'error' => 'Could not send invitation: ' . $result->error
        ]);
    }
}
```

## What Just Happened Behind the Scenes

Every time FrankPHP distributes an email:

1. **Context Handoff:** The controller receives an interactive action context and passes raw business targets to your injected application-owned service (here, `NotificationService`).
2. **Message Construction:** Your service builds an `EmailMessage` value object and hands it to the framework's `EmailService::send()` — the one place in the application that knows how to actually dispatch mail.
3. **Environment Assembly:** `EmailService` processes the request using values compiled from your secure `app/.env` file during the initial bootstrap timeline.
4. **Encapsulation & Dispatch:** The internal service encapsulates metadata securely into the immutable `EmailMessage` object, which is dispatched via SMTP.
5. **Upstream Response:** An `EmailResult` envelope returns upstream—providing the invoking controller explicit confirmation of delivery success or a clean, diagnostic error string on failure.

No magic background queues to stall out on shared hosting. Complete visibility, fast, and completely traceable.
