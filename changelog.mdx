# Changelog

This page records the public FrankPHP framework release history in a more readable form than the raw `CHANGELOG.md` file.

Use it when you want to understand what changed between framework versions, whether a release affects existing installs, and which documentation or migration notes should be reviewed before upgrading.

<Note>
For upgrade planning, read this page alongside **Revisions and Migrations**. The changelog explains what changed. The migration guidance explains how to apply those changes safely to an existing application.
</Note>

<Update label="30 September 2026" description="v2.1.0" tags={["Current", "Users", "Signup", "Migration"]}>
  ## Tenant-per-signup and Terms & Conditions acceptance

  FrankPHP 2.1.0 changes what a new sign-up means. **Every verified sign-up now creates its own tenant, and the person signing up becomes that tenant's `owner`.** Before this release every sign-up joined tenant 1 as a plain `user`, which blocked real self-service sign-ups on live apps.

  The tenant is named automatically from the sign-up email, with no extra form field. `jane@acme-corp.com` becomes "Acme Corp", and `jane.doe@gmail.com` becomes "Jane Doe's Workspace". The owner can rename it in Tenant Settings. The rule is swappable, so apps with a different model, such as joining an existing tenant, can replace it.

  The release also adds **opt-in Terms & Conditions acceptance** at sign-up. When enabled, FrankPHP refuses sign-ups that haven't accepted the terms, and records when they accepted and which version.

  New guides: [Users Overview](/users/overview), [New User Sign-up Flow](/users/signup-flow), [Tenants, Ownership & Roles](/users/tenants-and-roles), [Terms & Conditions Acceptance](/users/terms-acceptance), [Customising Sign-up](/users/customising-signup) and [Upgrading to 2.1.0](/users/upgrading-to-2-1-0).

  ### Added

  - `SignupTenantResolver`, the rule that decides which tenant and role a new user gets. The default, `CreateTenantForSignup`, creates a new tenant with the user as `owner`. Replace it with `$container->override()` in `app/bootstrap.php`.
  - Automatic tenant naming and unique slugs (`acme-corp`, `acme-corp-2`, …), with the tenant's company email set to the sign-up email.
  - `Database::transaction()`. Tenant, user and token are written together, so a failed sign-up never leaves an orphan tenant.
  - Opt-in config `signup.require_terms` and `signup.terms_version` in `app/Config/config.php`.
  - Columns `terms_accepted_at` and `terms_version` on `users` and `signup_tokens`.
  - `framework/sql/migrations/v2.1.0_signup_terms.sql`, an idempotent migration for existing installs.
  - `framework/Versions/FrankPHP_v2.1.0_migration_notes.md`.
  - `codebase.md` §16.9 "Signup: Tenant Creation and Terms Acceptance".
  - Starter app: Terms checkbox on the sign-up page, and a placeholder `/terms` page (`LegalController` and `Views/auth/terms.php`).

  ### Changed

  - `SignupService` no longer hardcodes tenant 1 and role `user`. It uses the `SignupTenantResolver`, enforces terms acceptance on the server when enabled, and keeps the acceptance if the code is resent.
  - The site-owner alert sent when an account is created now names the new tenant and role.
  - `SignupController` now also receives `UserService`.
  - The release zip now includes `Versions/` (migration notes) alongside `sql/migrations/`.

  ### Fixed

  - The automatic login after sign-up now records the login time. Previously a new user showed as "never logged in".
  - The starter verify page no longer auto-submits on the 6th digit. That could send a second request that logged the new user straight back out.

  <Warning>
  **Behaviour change for existing apps:** new sign-ups create their own tenant as `owner`. If your app needs sign-ups to join an existing tenant, override `SignupTenantResolver` before deploying. Existing installs must run the migration **before** turning on Terms acceptance. See [Upgrading to 2.1.0](/users/upgrading-to-2-1-0).
  </Warning>
</Update>

<Update label="29 September 2026" description="v2.0.1" tags={["Users", "Roles"]}>
  ## The `platform` role

  FrankPHP 2.0.1 introduces `platform` as a user role: a site-operator "super user" above tenant owners. It lays the foundation for cross-tenant access and for the new-tenant sign-up process in 2.1.0.

  ### Changed

  - The User Management dashboard now admits `platform` users as well as `admin` and `owner`.

  <Note>
  `platform` is not cross-tenant yet. A platform user still can't open another tenant's pages, and Tenant Settings is still limited to `admin` and `owner`. See [Tenants, Ownership & Roles](/users/tenants-and-roles).
  </Note>
</Update>

<Update label="6 August 2026" description="v2.0.0" tags={["Breaking", "Architecture", "Framework/App split"]}>
  ## The framework/application split

  FrankPHP 2.0.0 is the **framework/application split**: the single project folder is now two independent sibling folders, `framework/` and `app/`, each with its own PSR-4 namespace root (`Frank\` and `App\`, no searching or fallback between them). `framework/` contains nothing but framework-owned code and is meant to be replaced wholesale on every future update. `app/` — routes, business logic, views, public assets, config, `.env`, and `MYAPP.md` — is never touched by an update once you've customized it.

  This release is also the precursor to distributing FrankPHP through GitHub Releases rather than a single Gumroad zip.

  ### Added

  - `app/` as a sibling of `framework/` — the application half of the split: `Controllers/`, `Models/`, `Services/`, `Presenters/` (empty, ready for application code), plus `Views/`, `public/`, `Config/config.php`, `.env`/`env.example`, `MYAPP.md`, and `Scaffold/examples/` (cookbook-style reference implementations, moved out of live framework code, not deleted).
  - `Controllers/AccountSettingsController.php` — per-user account settings, no role restriction (distinct from the admin/owner-only `TenantSettingsController`).
  - `Container::override()` and `Router::override()` — the one supported way to deliberately replace a framework-registered binding or route from application code.
  - `Database::runSchemaFileIfMissingTable()` promoted to a general-purpose primitive — applications can now call it a second time for their own `app/sql/schema.app.sql`.
  - `config('mail.templates')` — optional per-application overrides for the three framework-required email templates (signup verification, password reset, platform-owner alert), without ever editing the framework's own template files.
  - `FRANK_VERSION` constant, read once from `framework/VERSION`.

  ### Changed

  - Every framework class renamed from `App\...` to `Frank\...`.
  - All framework routes now consistently use fully-qualified `Frank\Controllers\...` and `Frank\Middleware\...` handler/middleware strings.
  - `framework/bootstrap.php` now hard-requires `app/bootstrap.php` as its final step. A missing `app/bootstrap.php` is a fatal boot error by design.
  - `singleton()`/`bind()`/`add()` now throw on a duplicate id/route instead of silently allowing one component to shadow another — `override()` is the deliberate exception.
  - Fixed a real bug: `TenantSettingsController`'s forbidden-access check previously redirected a rejected user back to the exact same gated route, causing an infinite redirect loop. It now redirects to the tenant dashboard.
  - Fixed a schema-path resolution bug and a double database-seeding bug in `Core/Database.php`.
  - Removed hardcoded branding defaults from `EmailMessage`'s constructor — `from`/`fromName` are now required arguments on every call site.

  ### Removed

  - `cron_task_reminders.php` and its email template — a broken, unused feature referencing a `Task` model that never existed.
  - `POST /api/v1/tenant/{tenant_id}/organizations` is no longer a live framework route — moved to `app/Scaffold/examples/organization/` as a reference implementation.

  <Warning>
  This release renames every framework namespace from `App\` to `Frank\` and restructures the project into two sibling folders. Existing installs need a deliberate migration, not a file overwrite — see **Revisions and Migrations**.
  </Warning>
</Update>

<Update label="9 June 2026" description="v1.4.0" tags={["Admin", "Users", "Dashboard"]}>
  ## User Management Dashboard

  FrankPHP 1.4.0 introduces the framework's first built-in admin view: the **User Management Dashboard**, available to any user with role `owner` or `admin` at `GET /tenant/{tenant_id}/users`.

  The dashboard provides a tenant-scoped view of all users with four KPI stat cards and a full sortable user table, following the existing Service → Controller → View contract throughout — the view performs no computation.

  ### Added

  - `Services/UserManagementService.php` — new framework-owned singleton. `getUserDashboard()` computes four KPI stats (`totalUsers`, `activePercent`, `neverLoggedIn`, `inactiveThirtyDays`) from a single `User::allByTenant()` query, with no additional DB round-trips.
  - `Controllers/UserManagementController.php` — role-gates to `admin`/`owner`; non-privileged users are redirected to the dashboard with `?error=forbidden`.
  - `Views/users/management-dashboard.php` — stat cards and user table, all values pre-computed by the service.
  - `public/assets/css/app-pages-users.css` — `.stat-card`, `.users-table`, `.role-badge` and their variants.
  - `User::allByTenant(int $tenantId): array` — new model method; excludes sensitive columns.
  - Route `GET /tenant/{tenant_id}/users`, and a new **Users** sidebar nav entry.

  ### Changed

  - `CODEBASE.md` received a comprehensive accuracy pass: directory structure, container bindings table, CSS file table, design tokens, and framework table schemas (`tenants`, `users`, and `signup_tokens` documented in full) were all corrected against the actual filesystem.

  <Note>
  `signup_tokens.tenant_id` is NULL for the entire lifetime of an unverified token — no tenant exists until signup completes, so per-tenant scoping of unverified signup tokens is structurally impossible.
  </Note>
</Update>

<Update label="9 June 2026" description="v1.3.2" tags={["Core", "Models", "SoC", "Breaking"]}>
  ## Strict Model/Service separation of concerns

  FrankPHP 1.3.2 enforces a strict Model/Service separation of concerns across the entire framework. Models are now pure DB access layers — they never call `Clock` and contain no business logic.

  Previously, `User` and `Tenant` generated their own timestamps internally, `SignupService` duplicated signup-token DB access with raw PDO and SQL `NOW()`, and several model methods contained business logic (hash verification, rate-limit decisions, name derivation) that belonged in Services.

  ### Added

  - `Services/UserService.php` — new framework-owned singleton. `recordLogin()` and `saveSettings()` own the writable-column allowlist and null-coercion rules for user preferences, computing timestamps via `Clock`.
  - `Services/TenantService.php` — the parallel service for the tenant record.
  - `User::insertUser()`, `User::findPendingSignupTokens()`, `User::countRecentSignupTokensByIp()` — new model methods replacing private helpers that had mixed DB access with business logic.

  ### Changed

  - Every `Clock::nowUtcString()`/`Clock::utcOffsetString()` call removed from `Models/User.php` and `Models/Tenant.php` — all methods now accept pre-computed UTC timestamp strings from the calling Service.
  - `SignupService` no longer does raw PDO — all DB access now goes through `User` model methods; SQL `NOW()`/`DATE_SUB(NOW(), ...)` removed entirely.
  - `AuthController::login()` now calls `UserService::recordLogin()` instead of touching the `User` model directly.

  ### Build rules introduced

  - Models must never call `Clock`. All Clock calls live in Services; timestamps are passed down as explicit `string` parameters.
  - Models must not contain allowlists, field filtering, null-coercion, rate-limit comparisons, hash verification, or name derivation — these belong in Services.
  - SQL `NOW()`/`DATE_SUB(NOW(), ...)` must not appear in any model or service query.
</Update>

<Update label="6 June 2026" description="v1.3.0" tags={["Core", "Date/time", "Migration"]}>
  ## Formal date and time handling

  FrankPHP 1.3.0 introduces the framework's first formal date/time handling standard:

  > UTC at rest. Local at the edges.

  The headline addition is `Frank\Core\Clock`, a small framework-owned utility for UTC timestamp generation, UTC/local conversion, timezone validation, timezone resolution, and local-date query boundary calculation.

  This release is primarily a framework hygiene and portability release. It reduces the risk of timezone drift between applications, servers, databases, and users.

  ### Added

  - `Core/Clock.php` as a stateless static framework utility.
  - UTC timestamp helpers such as `Clock::nowUtcString()` and `Clock::utcOffsetString()`.
  - UTC normalisation helpers such as `Clock::toUtcString()` and `Clock::parseUtc()`.
  - Timezone validation and resolution helpers including `Clock::resolveTimezone()`.
  - Local input conversion helpers including `Clock::localInputToUtcString()`.
  - UTC-to-local display helpers including `Clock::formatUtcForTimezone()`.
  - Local date query-boundary helpers including `Clock::utcRangeForLocalDate()` and `Clock::utcRangeForLocalDates()`.
  - Local “now” helpers for display and input defaults only.
  - `CODEBASE.md` documentation for Date and Time Handling and Framework Core Utilities.

  ### Timezone resolution order

  FrankPHP now has a formal timezone resolution order:

  ```text
  user.timezone
  → tenant.timezone
  → config['timezone']
  → UTC
  ```

  Invalid or empty values are skipped. If no valid candidate is found, FrankPHP falls back to `UTC`.

  ### Build rules introduced

  - Use `Frank\Core\Clock` for persisted timestamp generation.
  - Store exact instants as UTC `DATETIME`.
  - Use `DATE` for date-only values with no time-of-day meaning.
  - Do not use SQL `NOW()` or `CURRENT_TIMESTAMP` for application-managed timestamps.
  - Do not calculate local date windows directly in SQL.
  - Convert local user, tenant, or application input into UTC before storage.
  - Convert UTC values into the resolved local timezone before display.
  - Resolve timezone explicitly using `Clock::resolveTimezone($user, $tenant, $config)`.
  - Do not let `Clock` read from `$_SESSION`, request globals, middleware state, controller globals, or the database.
  - Do not call `Clock` from views.
  - Services must prepare display-ready date labels for views.
  - Views must not perform timezone conversion, timestamp comparison, date fallback logic, or relative date labelling.
  - Document intentional application-level deviations in `MYAPP.md`.

  ### Migration notes

  Existing applications should add `Core/Clock.php` before refactoring date/time code.

  Search existing code for direct date/time handling:

  ```text
  date(
  time(
  strtotime(
  new DateTime(
  new DateTimeImmutable(
  NOW()
  CURRENT_TIMESTAMP
  ```

  Replace persisted timestamp generation with `Clock`, and replace relative SQL date filters with UTC boundary values calculated in PHP.

  Existing MySQL `TIMESTAMP` columns should be reviewed and classified before conversion. FrankPHP prefers UTC `DATETIME` for application-managed timestamps.

  When converting MySQL `TIMESTAMP` to `DATETIME`, run the migration session in UTC:

  ```sql
  SET time_zone = '+00:00';
  ```

  <Warning>
  Do not blindly convert date-only values. Values such as birthdays, anniversary dates, and local calendar-only due dates should use `DATE`, not `DATETIME`.
  </Warning>

  ### Fixed

  This release does not include a runtime bug fix by itself. It prevents future timezone and server portability bugs by defining a single framework-wide date/time contract.
</Update>

<Update label="13 May 2026" description="v1.2.0" tags={["Core", "DI", "Email", "Signup"]}>
  ## Dependency injection and signup email wiring

  FrankPHP 1.2.0 adds the framework's minimal dependency injection container and uses it to cleanly wire email-related services and controllers.

  ### Added

  - `Core/Container.php`, a minimal explicit DI container with `singleton()`, `bind()`, `make()`, and `has()`.
  - Container singleton registrations for `SignupService` and `PasswordResetService` in `bootstrap.php`.
  - Container bindings for `AuthController` and `SignupController`.
  - `EmailService::sendSignupVerification()` for signup verification emails.
  - `EmailService::sendCoachAdvisory()` for tenant-owner advisory emails.
  - `.env.example` key: `MAIL_ADVISORY_TO`.
  - CODEBASE documentation for the DI container, framework services, and signup routes.

  ### Changed

  - `Core/Router.php` now accepts an optional `Container` and checks for controller bindings before falling back to direct construction.
  - `AuthController` now receives `PasswordResetService` by constructor injection.
  - `SignupController` now receives `SignupService` by constructor injection.
  - `PasswordResetService` and `SignupService` no longer fall back to broken zero-argument `new EmailService()` construction.
  - Signup email methods now delegate to the injected `EmailService` instead of carrying SMTP details at the call site.
  - CODEBASE sections for request lifecycle, controllers, services, security notes, deliberate omissions, and framework ownership were updated.

  ### Fixed

  - Removed the `EmailService` construction failure caused by services falling back to `new EmailService()` without required SMTP configuration.
  - Removed hardcoded SMTP credentials from `SignupService`; credentials now flow from `.env` to `config['mail']`, into `EmailService::fromConfig()`, and then through the container singleton.
</Update>
